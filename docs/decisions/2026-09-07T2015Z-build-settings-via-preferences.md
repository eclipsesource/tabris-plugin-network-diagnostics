# Build settings are injected as Cordova preferences, not by a hook

Date: 2026-09-07

Superseded on 2026-09-08 by
`2026-09-08T1200Z-host-app-owns-required-configuration.md`. The preference
mechanism described below is still how the settings reach the Xcode project;
what changed is that the host application declares them, not the plugin.

## Context

A Tabris.js app is generated by the Tabris CLI from a cordova-ios fork. The
generated Xcode project declares no `SWIFT_VERSION` and an
`IPHONEOS_DEPLOYMENT_TARGET` of 11.0–12.0. This plugin is written in Swift and
its library needs iOS 16 (`ContinuousClock`, `Task.sleep(for:)`), so both
settings must be raised in every consuming app or the plugin does not compile.

The one existing Swift plugin in this family (`tabris-plugin-openidconnect`)
solves the Swift half with a Cordova hook that parses `project.pbxproj` with the
`xcode` npm module and writes `SWIFT_VERSION` into every build configuration.
That hook needs two npm dependencies, runs on three hook events, and edits the
generated project behind Cordova's back.

The cordova-ios fork shipped with the Tabris CLI reads two preferences from the
platform `config.xml` on every `prepare`: `deployment-target` becomes
`IPHONEOS_DEPLOYMENT_TARGET` and `SwiftVersion` becomes `SWIFT_VERSION`
(`bin/templates/scripts/cordova/lib/prepare.js`). Plugin `<config-file>` munges
are applied to that platform `config.xml` before the preferences are read, and
the app's own `config.xml` is merged on top, so an application preference wins
over a plugin's.

## Decision

`plugin.xml` injects

```xml
<config-file target="config.xml" parent="/*">
  <preference name="deployment-target" value="16.0" />
  <preference name="SwiftVersion" value="5.0" />
</config-file>
```

No hook, no npm dependencies. An app that already declares either preference
keeps its value; an app that declares a deployment target below 16.0 fails at
compile time with availability errors, and the README names the requirement.

Swift language mode stays 5. The library compiles in both modes; mode 6 on the
whole app target would also apply to every other plugin and to the generated
Objective-C-bridged code, which is not this plugin's decision to make.

## Consequences

- The consumer app's minimum iOS version becomes 16.0 unless it was already
  higher. README states it under Requirements.
- Verification of the build settings must read the *resolved* values
  (`xcodebuild -showBuildSettings`), not only grep the project file.
- Should a future cordova-ios version stop honouring the preferences, the
  fallback is the openidconnect-style hook extended with the deployment target.
  The verification step in the example build catches that regression.

## Rejected alternatives

- **Cordova hook editing `project.pbxproj`** (openidconnect): works, but adds
  `xcode` and `semver` dependencies, fires on three events with command-line
  guards, and mutates the generated project outside Cordova's model.
- **`@available(iOS 16, *)` on the plugin class**: the Tabris runtime
  instantiates registered classes by name at startup regardless of availability
  annotations, so the guard cannot degrade gracefully.
- **Documenting the preferences only and leaving them to the app**: every
  consumer would fail on first build; the plugin knows its own requirements.
- **Raising the floor to 17 and keeping `AsyncStream.makeStream`**: iOS 17 buys
  nothing the library needs (see the package decision record).
